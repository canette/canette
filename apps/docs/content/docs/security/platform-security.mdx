This page covers the security properties of canette at runtime — how credentials are stored, how users are authenticated, how the API is protected, and how traffic reaches your apps. For security concerns specific to the image build process, see [Build security](/docs/concepts/build-security).

---

## Secrets and credentials

### App secrets (environment variables)

App secrets are encrypted before they are written to the database and decrypted only at deploy time.

- **Algorithm**: AES-256-GCM with a random 96-bit nonce per value
- **Key**: a master key stored in a Kubernetes `Secret` in the `canette-system` namespace, created once at Helm install time and never written to the database
- **At deploy time**: the API decrypts the value in memory and creates a Kubernetes `Secret` in the app's namespace; the plaintext value exists only for the duration of that operation
- **Never returned**: the API does not return secret values after they have been stored — not in list responses, not in detail responses, not in logs
- **Never logged**: secret values are excluded from structured logging at every log level

### Registry pull credentials

When `controller.imagePullSecrets.enabled=true`, the controller creates a `canette-registry-creds` Secret in every app namespace so the kubelet can pull images. This Secret is in the same namespace as the app workload.

**Trade-offs to be aware of:**

- Any pod that gains Kubernetes API access and secret-read RBAC in its namespace can read the pull credential. canette does not grant this by default, but a misconfigured role in the app namespace would expose it.
- For the in-cluster registry, pull and push credentials are the same — a leaked pull secret therefore grants write access to the registry. For external registries, configure `externalRegistry.pullUsername`/`pullPassword` with a read-only account to scope the credential to pulls only.

The safest configuration is to provision registry access at the node level (containerd credential provider or `/etc/containerd/certs.d/`) and set `controller.imagePullSecrets.enabled=false`. This removes the Secret from app namespaces entirely. See [Image pull credentials](/docs/self-hosting/registry#image-pull-credentials) for setup details.

### Git credentials (PAT tokens and SSH keys)

Git credentials (PAT tokens and SSH private keys) use the same AES-256-GCM encryption as app secrets. The master key is the same shared key. Credentials are scoped to a project; apps within the project inherit them.

The `known_hosts` fingerprint for SSH credentials is not secret and is stored in plaintext.

## Authentication

Authentication is handled by [better-auth](https://www.better-auth.com) embedded in the API server.

### Supported providers

| Provider | Notes |
|----------|-------|
| GitHub OAuth | Recommended for teams already on GitHub |
| Google OAuth | Requires a Google Cloud OAuth app |
| Email/password | Always available; new sign-ups can be disabled via Helm |

### Session handling

- Sessions are stored server-side; the browser receives a signed, `HttpOnly` session cookie
- The UI communicates with the API exclusively via this session cookie — it never holds or exposes an API token
- CI/CD integrations use `Authorization: Bearer <token>` — tokens are scoped and can be rotated independently of user sessions

### Access control

- **401 Unauthenticated**: returned when no valid session or token is present
- **403 Forbidden**: returned when a valid session exists but the user does not have access to the requested project or app
- Project membership is explicit — users do not get access to resources they have not been granted

## Webhook security

Webhooks from GitHub, GitLab, and Gitea are validated with HMAC before any processing occurs.

- Each webhook endpoint has a per-project secret stored in the database
- Incoming requests are rejected immediately if the `X-Hub-Signature-256` (or equivalent) header is absent or does not match
- Validation happens before any payload parsing — an invalid signature produces no side effects

## API design

- All endpoints require authentication; there are no unauthenticated read endpoints
- The API server does not talk to the Kubernetes API directly — that is the controller's responsibility. A compromised API process cannot create, modify, or delete Kubernetes resources
- The UI talks only to the API — it has no direct database access and no Kubernetes credentials
- Paginated list responses include only the fields needed for display; encrypted values are never included

## Network routing

canette uses the [Kubernetes Gateway API](https://gateway-api.sigs.k8s.io/) exclusively — no legacy `networking.k8s.io/v1 Ingress` resources are generated.

- Each app gets an `HTTPRoute` that routes from the cluster gateway to the app's `Service`
- The `gatewayClassName` is set via Helm values — canette does not hardcode any controller-specific behaviour
- Traefik is included as a subchart and enabled by default; it can be replaced with any Gateway API-compatible controller

## Namespace isolation

canette uses three tiers of namespaces:

| Namespace | Contents |
|-----------|----------|
| `canette-system` | canette control plane services (API, UI, controller, builder daemon, registry) |
| `canette-build` | ephemeral build jobs — isolated from apps and control plane |
| `can-{id}-{slug}` | one namespace per project, containing app `Deployment`, `Service`, `HTTPRoute`, and `Secret` resources |

Build jobs cannot reach app namespaces or the control plane namespace. App namespaces cannot reach `canette-system` directly — all communication goes through the API.

### Pod Security Admission

Every project namespace carries [Pod Security Admission](https://kubernetes.io/docs/concepts/security/pod-security-admission/) labels. They give a cluster-enforced safety net that doesn't depend on what the controller generates:

| Label | Default | Effect |
|-------|---------|--------|
| `pod-security.kubernetes.io/enforce` | `baseline` | Kubernetes rejects pods that break the [baseline](https://kubernetes.io/docs/concepts/security/pod-security-standards/#baseline) level, such as privileged containers, host networking or `hostPath` volumes. |
| `pod-security.kubernetes.io/warn` | `restricted` | Kubernetes returns a warning when an app doesn't meet the stricter `restricted` level. The controller logs each warning once. These show which apps could run in hardened mode. |
| `pod-security.kubernetes.io/audit` | `restricted` | Same check, recorded in the API server audit log. |

Ordinary apps meet `baseline` without changes. Set the levels with the `controller.podSecurity.*` Helm values, or set one to `""` to drop that label. A namespace gets the new labels on its next deploy. Pods that are already running are never evicted.

### Resource quotas (optional)

Admins can cap what one project may use in total with a `ResourceQuota` (`canette-quota`), and limit single containers or volumes with a `LimitRange` (`canette-limits`). Both are off by default and configured with the `controller.namespaceQuota` and `controller.namespaceLimitRange` Helm values. When a quota is set, leave room for one extra pod: a rolling update starts the new pod before stopping the old one.

## App workload defaults

Every app canette deploys gets these settings. They need no configuration and don't break normal apps, whether built by railpack or deployed from any Docker image.

**Pod**

| Setting | Why |
|---------|-----|
| `automountServiceAccountToken: false` | Apps never need the Kubernetes API. Without a token, a compromised app can't use the API to read Secrets in its namespace, such as the registry pull credentials. |
| `enableServiceLinks: false` | All apps in a project share a namespace. Kubernetes would otherwise inject variables like `REDIS_PORT=tcp://10.0.0.5:6379` for every sibling Service, which breaks apps that expect a port number in `REDIS_PORT`. Reach other apps by DNS name instead (`<app-slug>.<namespace>.svc.cluster.local`). |
| `seccompProfile: RuntimeDefault` | Blocks rarely needed, risky syscalls using the container runtime's default profile. |
| `allowPrivilegeEscalation: false` (app container) | Blocks gaining privileges through setuid binaries such as `sudo`. An image that starts as root and drops to another user with `gosu`/`su-exec` still works. |
| `terminationGracePeriodSeconds: 30` | Explicit time an app gets after SIGTERM to shut down cleanly. |

**Deployment** (web and private apps)

- **Rollout strategy:** apps without a persistent volume use a rolling update with `maxUnavailable: 0` and `maxSurge: 1`, so the new pod is ready before the old one stops. Apps with a persistent volume use `Recreate`, because a `ReadWriteOnce` volume can only be attached to one node at a time and a rolling update could get stuck. This means a short downtime on each deploy for apps with a persistent volume (see [Volumes](/docs/configuration/volumes#how-apps-with-a-persistent-volume-are-deployed)).
- **History:** only the last 3 old ReplicaSets are kept (`revisionHistoryLimit`).
- **More than one replica** (not possible for apps with a persistent volume): pods are spread across zones and nodes where possible (`topologySpreadConstraints` with `ScheduleAnyway`), and a `PodDisruptionBudget` with `maxUnavailable: 1` stops a node drain from taking every replica down at once. The budget is removed when the app goes back to one replica.

**CronJob**

- Runs that couldn't start within 5 minutes of their schedule (for example after cluster downtime) are skipped instead of all running at once (`startingDeadlineSeconds: 300`).
- A failed run is retried at most 2 times (`backoffLimit: 2`).
- A run is stopped after 6 hours (`activeDeadlineSeconds: 21600`). Runs never overlap, so a hung run would otherwise block every later run.
- Finished Jobs and their pods are deleted after 1 day (`ttlSecondsAfterFinished: 86400`).

All numbers can be changed with the `controller.workloads.*` Helm values. Stricter settings (non-root user, read-only root filesystem, dropped capabilities) can break some images and are not on by default.

## Deployment snapshots

When a deploy is triggered, the API writes a snapshot of all configuration into the `deployments` table — git URL, branch, resource defaults, environment variables, and scan policy at the exact moment of triggering.

This means:
- The controller and builder read the snapshot, not live tables — a configuration change after triggering does not affect an in-progress build
- Encrypted secrets are read once at deploy time and passed to Kubernetes; they are not re-read or re-decrypted during the lifetime of the deployment
- The snapshot is intentionally denormalised — the builder and controller do not need to join multiple tables, reducing the blast radius if any single table is compromised
