A **deployment** is a single attempt to build and ship a commit of an app.

## Status lifecycle

| Status | Meaning |
|---|---|
| `pending_build` | Queued, waiting for the builder to pick it up |
| `building` | Build Job is running (git-clone → image-build → push) |
| `scanning` | Image pushed, vulnerability scan running (only when [scanning](/docs/security/build-security#image-content) is enabled) |
| `pending_deployment` | Image ready, waiting for the controller to pick it up. Image apps and redeploys start here |
| `deploying` | Controller applying K8s manifests |
| `live` | Deployment is running and passing health checks |
| `failed` | Build or deploy failed — see logs for details |
| `stopped` | App was manually stopped — K8s resources have been torn down |
| `superseded` | Replaced before it went live, by a Stop or a newer deployment, or replaced by a newer deployment that went live. A build that finished keeps its image, so it can be redeployed. A build cancelled while it ran has none |

Stopping an app is final for the deployments in progress: a running build is cancelled, and a rollout is stopped. Only a new deploy or redeploy runs the app again.

A new deploy or redeploy doesn't wait for one in progress: it replaces it. A build that is still running is cancelled. A rollout that is still running finishes first, because it is what serves until the new deployment is ready.

The app's status in the UI and in the MCP `get_app` tool (`lifecycleStatus`) follows what the app should run, not its newest deployment: `building`, `deploying`, `live`, `failed`, `stopping` (stopped, still being torn down) or `stopped`.

For an app with a public URL, a deployment goes `live` only once the Gateway has accepted its HTTPRoute. If the Gateway rejects the route, for example because no listener allows one of the app's hostnames or because it can't resolve the backend Service, the deployment fails with the Gateway's reason. A Gateway that hasn't reported on the route within two minutes doesn't fail the deployment: it goes live with a warning in the deploy log. canette checks the route only during a deploy. If a Gateway change later stops routing the app, a cluster admin has to fix the Gateway.

If the controller restarts during a rollout, the next controller picks the deployment up again within a few minutes and finishes it, rather than failing it.

## Runtime health

Separate from deployment status, the app page also shows an **Unhealthy** indicator when the last deploy succeeded but the running pod is currently misbehaving. This can appear at any time after a deploy — for example if the app crashes hours after going live — and clears automatically once the pod recovers.

canette confirms each app's health every few minutes. If it can't confirm it for 10 minutes, for example because the controller is down or can't reach Kubernetes, the health is reported as unknown: the app page shows no indicator, and the MCP `get_app` tool returns `unknown`.

| Reason | Meaning |
|---|---|
| `CrashLoopBackOff` | The app keeps crashing right after it starts, so Kubernetes is repeatedly restarting it with a growing delay between attempts |
| `ImagePullBackOff` | Kubernetes couldn't download the container image and is waiting before trying again |
| `ErrImagePull` | Kubernetes couldn't download the container image — it may not exist, or access may be denied |
| `{reason} (exit {code})` | The app's process exited unexpectedly with the given exit code (e.g. `OOMKilled (exit 137)` means it ran out of memory) |
| `restarting repeatedly` | The app has restarted several times in the last few minutes, which usually means it's failing shortly after startup |
| `readiness probe failing` | The app is running, but it isn't passing the health checks it needs to pass before it can receive traffic |
| `no running pods` | There's no running instance of this app right now |

No indicator is shown while a deployment has no pods yet (e.g. just after triggering) or while the app is healthy.

## Kubernetes readiness

Next to runtime health, a live app can show a second indicator with what Kubernetes itself reports for the app's workload. Runtime health is about the running pods. Kubernetes readiness is about the Deployment or CronJob that owns them.

| Indicator | Meaning |
|---|---|
| `2/3 available` | Fewer replicas are available than configured, so the app is serving at reduced capacity. `0/n available` means it isn't serving traffic |
| `Deployment missing` / `CronJob missing` | The workload doesn't exist in Kubernetes, for example because it was deleted outside canette. Redeploy to recreate it |
| `Suspended` | The CronJob is suspended in Kubernetes, so no new runs start on schedule |
| `Last run failed` | The CronJob's most recent run failed |
| `Not run yet` | The schedule hasn't triggered a run yet. This is normal for a new or rarely scheduled job, not an error |

canette reads this from Kubernetes about once a minute and applies the same 10-minute rule as runtime health: a reading older than that isn't shown, and the MCP `get_app` tool leaves `kubernetesStatus` out. No indicator is shown at full capacity or when the latest run succeeded.

## Triggering a deployment

Deployments can be triggered:

- **Manually** from the app page in the UI
- **Via webhook** from GitHub, GitLab, or Gitea on push

## Deploy actions

The app page exposes up to three deploy actions depending on the app's current state:

### Redeploy

Creates a new deployment record that reuses the **same image** as the current deployment, skipping the build. Settings (port, environment variables, secrets) are read fresh when you click it, so any changes you saved since the last deploy are picked up without requiring a rebuild.

Use **Redeploy** when:
- You changed an environment variable, secret, or port and want to apply it to the running app
- You want to restart the app without pulling a new image

### Rebuild (git apps)

Creates a new deployment record and triggers a full build: git clone at the latest commit on the configured branch → Railpack build → image push → deploy.

Use **Rebuild** when:
- You have pushed new code and want to pick it up

### Deploy new (image apps)

Creates a new deployment record and re-resolves `imageUrl:imageTag` at deploy time. If the tag (e.g. `latest`) has been updated in your registry since the last deploy, the new image version is used.

Use **Deploy new** when:
- You have pushed a new image to your registry and want to pull it

## Viewing logs

Two log views are available from the app page:

- **Deploy logs** — output from the build pipeline and Kubernetes rollout, scoped to a specific deployment. Available for all apps regardless of source type.
- **App logs** — live stdout/stderr streamed directly from the running container over SSE. Only available while the app is `live`. Logs are not stored — open the panel to start a live stream.
