canette exposes a [Model Context Protocol](https://modelcontextprotocol.io) server at `/mcp` on your instance. AI agents can use it to deploy repositories, check deployment status, and diagnose failures — all through natural language instructions.

## Connecting an AI client

The MCP server uses the [Streamable HTTP transport](https://modelcontextprotocol.io/specification/2025-03-26/basic/transports) and authenticates via OAuth 2.1 with PKCE. When you connect for the first time, your client will open a browser window where you log in with your existing canette credentials — the same GitHub, Google, or email login you use in the UI.

### Claude Code

Run this command to register canette as an MCP server in Claude Code:

```sh
claude mcp add --transport http canette https://your-canette.company.com/mcp
```

Or add it manually to `~/.claude/claude_code_config.json` (or the project-level `.claude/settings.json`):

```json
{
  "mcpServers": {
    "canette": {
      "type": "http",
      "url": "https://your-canette.company.com/mcp"
    }
  }
}
```

Replace `your-canette.company.com` with your instance's hostname. Claude Code will prompt you to authenticate in the browser the first time it connects.

### Cursor

In Cursor, open **Settings → MCP** and add a new server:

- **Name:** canette
- **Type:** HTTP
- **URL:** `https://your-canette.company.com/mcp`

### Other clients

Any MCP client that supports the Streamable HTTP transport and OAuth 2.1 can connect. Point it at `https://your-canette.company.com/mcp`. The OAuth discovery document is at `https://your-canette.company.com/.well-known/oauth-authorization-server`.

## Authentication

The MCP server uses standard OAuth 2.1 with PKCE. You do not need to create or manage API tokens manually.

1. The client discovers the OAuth endpoints from `/.well-known/oauth-authorization-server`
2. The client opens a browser to `https://your-canette.company.com/oauth/authorize`
3. If you are not already logged in, you are redirected to the canette login page
4. After login, the client receives an access token automatically
5. The token is valid for 1 hour; the client will re-authenticate when it expires

An access token is tied to the browser session you authorized it from. Signing out of canette in that browser ends the client's access immediately, and the client will ask you to authorize again.

## Available tools

| Tool | Description |
|------|-------------|
| `list_projects` | List all projects you have access to |
| `list_apps` | List apps within a project |
| `create_project` | Create a new project (uses your personal team by default) |
| `create_app` | Create an app in a project — built from a Git repository (including monorepo subdirectories and private repositories) or run from a Docker image, as a `web`, `private` or `cronjob` app |
| `update_app` | Change an existing app's settings, such as branch, port, image tag or its [canette.yaml config](#runtime-config-canetteyaml) — applied on the next deployment (a rebuild for source changes, a redeploy for runtime settings) |
| `list_git_credentials` | List the Git credentials a project can use for private repositories (names and types only, never tokens or keys) |
| `trigger_deployment` | Build and deploy an app from its source — fetches the latest commit and runs a full build for a Git app. For the first deployment and whenever the code or source changed |
| `list_deployments` | List recent deployments for an app — use this to find a `deployment_id` when troubleshooting a deployment not triggered in this session |
| `get_deployment` | Get the status and details of a deployment — provide `app_id` for the latest, or `deployment_id` for a specific one |
| `get_build_logs` | Fetch full build logs for a deployment — useful for diagnosing build failures |
| `redeploy_deployment` | Deploy an already-built image again, without rebuilding, using the app's current settings and environment — to apply configuration changes or to roll back |
| `get_app` | Get an app's current state — live URL, custom hostnames, latest deployment and runtime health |
| `get_runtime_logs` | Fetch recent logs and pod status (restarts, `CrashLoopBackOff`, exit code) from the running app. Automatically returns the crashed container's logs when the app is crash-looping |
| `get_app_metrics` | Get per-pod readiness, restarts, last termination reason (e.g. `OOMKilled`) and CPU/memory usage. Usage requires metrics-server on the cluster |
| `list_env_vars` | List an app's environment variables and the names of its secrets (secret values are never returned) |
| `set_env_var` | Create or update a plaintext environment variable — applied on the next deployment, a redeploy is enough |
| `delete_env_var` | Delete an environment variable — applied on the next deployment, a redeploy is enough |
| `request_secret` | Ask you to enter one or more secrets on a canette page, so the values never pass through the agent ([details](#secrets)) |
| `search_docs` | Search the canette documentation and return the best-matching sections with their page path |
| `get_docs_page` | Get one documentation page as markdown, e.g. `configuration/canette-yaml` |
| `get_canette_yaml_schema` | Get the JSON Schema for `canette.yaml` or `canette-template.yaml`: every field with its type, allowed values and description |

### Secrets

No MCP tool accepts or returns a secret value, because anything a tool receives ends up in the AI client's conversation and logs. Agents can see which secret names exist (`list_env_vars`), and when an app needs one they call `request_secret` with the names and an optional reason. It returns a link like:

```
https://canette.example.com/dashboard/projects/my-project/apps/my-app/request-secrets?keys=DATABASE_URL,STRIPE_KEY
```

You open the link, enter the values and save. They go straight to canette, encrypted, through your normal browser session. Then tell the agent you're done: it checks with `list_env_vars` that the secrets exist and redeploys the app.

- The link grants nothing. It only works for a logged-in member of the app's team, so it is safe in the agent's context and logs. If you are logged out, canette sends you back to the page after you log in.
- The reason is written by the agent. canette shows it as plain text, labelled as coming from the agent. Check that the request makes sense before you enter a value.
- If a name already exists as a secret, saving replaces its value. If it exists as a plain environment variable, the page offers to convert it to a secret and deletes the plaintext value.
- Secrets can't be deleted through MCP. Delete them under **Settings → Environment**.

### Rebuild or redeploy

There are two ways for an agent to start a deployment, and the server tells the agent which one to use:

- **`trigger_deployment`** builds the app from its source and then deploys it. For a Git app that means fetching the latest commit and running a full image build, which takes minutes. It is needed when the source changed: new commits, or a different repository, branch, app path, Git credential or image tag.
- **`redeploy_deployment`** deploys an image that is already built, with the app's current settings, environment variables and secrets. It takes seconds. It is enough when only configuration changed: environment variables, secrets, port, schedule, deployment type, canette.yaml config, volumes, hostnames or password protection.

Environment variables are injected when the app starts, not when it is built, so changing one never requires a rebuild. After `set_env_var`, `delete_env_var` or a runtime-only `update_app`, the tool result tells the agent to redeploy the app's latest live deployment. You should not have to spell this out in your prompt.

### Runtime config (canette.yaml)

`create_app` and `update_app` take a `canette_config` argument: the app's [canette.yaml](/docs/configuration/canette-yaml) stored on the app, the same document as the canette.yaml field in the app settings. Agents use it to change resources, replicas, health checks, the start command, ingress or [hardened mode](/docs/security/hardened-mode) (`security`) without a commit. It is the only way to do this for an app run from a Docker image, which has no repository.

- The value is the complete document and **replaces** the stored one; it is not merged. The agent reads the current value with `get_app` first.
- For a Git app, a `canette.yaml` committed to the repository wins field by field after the build, so the agent should check the repository first.
- `build` fields apply only to Git apps, at the next build, and a `canette.yaml` in the repository wins over them.
- `null` or an empty string clears it.
- Invalid YAML is rejected with the line and column of the error, so the agent can fix it.
- Runtime fields are applied by a redeploy, no rebuild is needed.
- An invalid `security` block fails the next deployment with a message naming the field. When an agent hardens an app and also changes its `Dockerfile`, a new build (`trigger_deployment`) is needed, not a redeploy.

### Documentation

The MCP server includes these docs, taken from the same canette release as your instance. Agents read them with `search_docs` and `get_docs_page`, so what they read always matches the features your instance supports, even if canette.dev already documents a newer release. This also works when the agent can't reach the internet.

The server tells agents to read the canette.yaml reference before writing a `canette.yaml`, a `canette-template.yaml` or `canette_config`. Clients that support MCP resources can also browse every page as a `canette-docs://<path>` resource, e.g. `canette-docs://configuration/canette-yaml`.

The [JSON Schemas](/docs/configuration/canette-yaml#json-schema) for `canette.yaml` and `canette-template.yaml` are bundled the same way. Agents read them with `get_canette_yaml_schema`, or as the `canette-schema://canette.json` and `canette-schema://canette-template.json` resources.

### Example prompts

**Deploying a repository:**
> "Add my repo `https://github.com/myorg/my-app` to canette and deploy it"

The agent will create a project, create an app pointing at the repository, and trigger the first deployment.

**Troubleshooting a failure:**
> "My canette app `my-app` is failing to deploy — what's wrong?"

The agent will fetch the latest deployment status and build logs, then explain the error.

**Debugging a running app:**
> "`my-app` deployed but returns 502 — why?"

The agent will check the app's state, read the runtime logs and pod status (including the output of a crashed container), and look at memory usage to spot an `OOMKilled` restart.

**Fixing missing configuration:**
> "`my-app` crashes on startup — fix it"

The agent will read the runtime logs, spot a missing variable such as `LOG_LEVEL`, set it and redeploy the existing image without rebuilding. If the missing value is a secret (for example `DATABASE_URL`), it will give you a link to [enter it in canette](#secrets) and redeploy once you say you're done.

**Changing configuration:**
> "Set `LOG_LEVEL` to `debug` on `my-app`"

The agent will set the variable and redeploy the app's current image. No build runs, so the change is live in seconds.

**Changing resources:**
> "Give `redis-cache` a 512Mi memory limit"

For an app run from a Docker image, the agent will read the app's current canette.yaml with `get_app`, add the limit under `resources.limits.memory`, save the complete document with `update_app` and redeploy:

```yaml
resources:
  limits:
    memory: 512Mi
```

**Rolling back:**
> "The latest deploy of `my-app` is broken — roll back to the previous version"

The agent will list recent deployments, pick the last one that was live, and redeploy its image. The rollback uses the app's current settings and environment variables, not the ones from the earlier deployment.

## Prerequisites

The MCP server requires `MCP_JWT_SECRET` to be set. If you installed canette via Helm, this secret is auto-generated on first install and stored in the `canette-api-secrets` Kubernetes Secret. No manual configuration is needed for a standard install.

See [Helm configuration](#helm-configuration) below if you need to rotate the key or use an external secret.

## Helm configuration

The `MCP_JWT_SECRET` is stored in the `canette-api-secrets` Kubernetes Secret and auto-generated on first install. You can override this behaviour:

**Provide your own value** in `values.yaml`:

```yaml
api:
  mcpJwtSecret: "your-secret-here"  # min 32 characters
```

**Use a pre-existing Kubernetes Secret** (useful when secrets are managed externally):

```yaml
api:
  mcpJwtSecretRef:
    name: my-external-secret
    key: mcp-jwt-secret
```

The secret must exist in the canette namespace before running `helm install` or `helm upgrade`.

<Callout type="info">
  Rotating `MCP_JWT_SECRET` invalidates all existing access tokens. Connected clients will re-authenticate automatically on their next request.
</Callout>
