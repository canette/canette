Commit a `canette.yaml` file to your repository to customise build and runtime behaviour. All fields are optional — absence means "use platform defaults".

## Full reference

The complete format is also published as a [JSON Schema](#json-schema), with a description of every field.

```yaml
# yaml-language-server: $schema=https://canette.dev/schema/canette.json

build:
  context: .            # path relative to app root
  dockerfile: Dockerfile
  args:
    KEY: value

runtime:
  port: 3000
  command: ["node", "server.js"]

env:
  KEY: value            # plaintext, safe to commit

secrets:
  - SECRET_NAME         # names only — values are set in the UI

resources:
  requests:
    cpu: "100m"
    memory: "128Mi"
  limits:
    cpu: "500m"
    memory: "512Mi"

replicas: 1

healthcheck:
  path: /healthz
  port: 3000
  initial_delay: 10
  period: 15

ingress:
  enabled: true         # set to false to suppress the HTTPRoute (private-equivalent override)

security:
  hardened: true        # opt-in: non-root, read-only root filesystem, no capabilities
  writable_paths: ["/tmp"]
```

## Field ownership

Fields are split between the UI (stored in the database) and `canette.yaml` (committed to the repo). The file is parsed at deploy time — not on every UI interaction — so there is no sync problem.

| Field | Owned by | Behaviour |
|-------|----------|-----------|
| `build.context`, `build.dockerfile`, `build.args` | `canette.yaml`, or the app's stored config as a fallback | Read at build time, Git apps only |
| `runtime.port`, `runtime.command`, `replicas`, `resources`, `healthcheck` | UI as default, `canette.yaml` overrides | File wins when present; UI value is the fallback |
| `env` | `canette.yaml` only | Plaintext vars committed to the repo; merged at deploy time |
| `secrets` | UI only (values); `canette.yaml` can list names | Secret values are never stored in the file |
| `security` | `canette.yaml` only | Opt-in [hardened mode](/docs/security/hardened-mode). An invalid `security` block fails the deployment instead of being ignored |
| `ingress.enabled` | UI as default, `canette.yaml` overrides | `false` suppresses the HTTPRoute for this deployment only — equivalent to setting the app's visibility to Private in the UI |

## Build detection

When a deployment is triggered, canette determines the build method in this order:

1. **`build.dockerfile` is set** in `canette.yaml` — uses the Dockerfile at that path (relative to the app root), with `build.context` as the build context
2. **`Dockerfile` exists at the app root** — auto-detected, no `canette.yaml` needed
3. **Neither** — [railpack](https://railpack.com) auto-detects the project type and builds it

## Notes

- Unknown fields are silently ignored (forward compatibility). If the file can't be read (invalid YAML or a value of the wrong type), the deploy log shows a warning and the rest of the file is ignored. The `security` block is read separately: it still applies, and if it is invalid itself, the deployment fails
- `security.hardened: true` usually needs no other change, but some images need extra writable directories or a different port. See [Hardened mode](/docs/security/hardened-mode)
- `env` values are stored in plaintext in your repo — do not put secrets here
- `secrets` lists names only; values must be set via the UI or API
- With `replicas` greater than 1, pods are spread across nodes and zones where possible, and a disruption budget keeps node drains from stopping more than one at a time. See [App workload defaults](/docs/security/platform-security#app-workload-defaults). Apps with a [Persistent Volume](/docs/configuration/volumes#how-apps-with-a-persistent-volume-are-deployed) are limited to 1 replica
- `build.context` and `build.dockerfile` are paths relative to the app root (the directory set as **App path** in the UI), not the repo root
- The same document can also be stored on the app itself, from the app settings in the UI or by an AI agent through [MCP](/docs/ai-agents/mcp#runtime-config-canetteyaml). This is the only option for apps run from a Docker image. A stored document is checked for valid YAML when it is saved and is limited to 10 KB. Its `build` fields apply only to Git apps, at the next build. For a Git app, a `canette.yaml` committed to the repository wins field by field over the stored one

## JSON Schema

canette publishes a JSON Schema for `canette.yaml` at [`https://canette.dev/schema/canette.json`](https://canette.dev/schema/canette.json). It is generated from the same Go types that canette uses to read the file, so it lists every field the platform supports, with its type, allowed values and a description.

To get autocomplete and validation in your editor, add this line at the top of your `canette.yaml`:

```yaml
# yaml-language-server: $schema=https://canette.dev/schema/canette.json
```

This works in any editor that uses [yaml-language-server](https://github.com/redhat-developer/yaml-language-server), such as VS Code with the Red Hat YAML extension, Neovim and Zed.

The schema allows fields it doesn't know, the same as canette does, so a typo in a field name isn't reported as an error. AI agents connected through [MCP](/docs/ai-agents/mcp#documentation) can read the schema with the `get_canette_yaml_schema` tool, which returns the version that matches your instance.
