**Password protection** puts a password in front of a web app's public URL. It's useful for demos, previews and Storybooks that shouldn't be open to everyone but don't need real user accounts.

There is one shared password per app, not individual accounts. canette stores only a bcrypt hash of it, and never shows it again after you save it.

<Callout type="info">
  Password protection is only available for **Public** (`web`) apps. Private and scheduled apps have no public URL to protect. See [Deployment type](/docs/concepts/apps#deployment-type).
</Callout>

## Turning it on

Open the app's **Settings → Password protection**, click **Enable password protection** and enter a password. The same section changes the password or turns protection off.

Like other settings, the change takes effect on the **next deployment**. A redeploy of the current deployment is enough; no rebuild is needed.

You can also ask an AI agent connected through [MCP](/docs/ai-agents/mcp#password-protection). The agent never sees the password: it gives you a link to a canette page where you set it yourself.

## How visitors sign in

- **Browsers** get a login form. After a correct password, a signed session cookie keeps the visitor signed in for 24 hours. Visitors can sign out at `/.canette-gate/logout`.
- **Scripts, webhooks and CI** can skip the form and send the password with HTTP Basic auth. Any username is accepted, for example:

  ```bash
  curl -u any:my-password https://my-app-my-project.example.com/api/health
  ```

  The sidecar removes the `Authorization` header from these requests before forwarding them, so your app (and its request logs) never see the password. Requests from a signed-in browser keep any `Authorization` header they send, such as your app's own Bearer token.

Changing the password signs out every visitor, because the session cookie is derived from the password hash. There is no separate key to rotate.

## How it works

When protection is on, canette adds a small sidecar container to the app's pod. The sidecar receives all traffic, checks the password, and forwards authenticated requests to your app on `localhost`. Your app needs no changes.

Two things are reserved for the sidecar:

- **Paths under `/.canette-gate/`** (the login form, logout and health check) are handled by the sidecar and never reach your app.
- **Port `39191`** is used by the sidecar, so your app can't listen on it.

The sidecar always runs with a [hardened](/docs/security/hardened-mode) security context, whether or not the app itself is hardened.

## Limits

- Passwords can be at most **72 bytes** (bcrypt's limit). canette rejects longer passwords instead of silently ignoring the rest.
- Password protection can't be set in `canette.yaml` or in a [template](/docs/configuration/templates). It is configured on the app after it exists.
- It protects the platform-generated URL and any custom hostnames alike, since they all route to the same sidecar. Traffic from inside the cluster to the app's Service also goes through the sidecar.
